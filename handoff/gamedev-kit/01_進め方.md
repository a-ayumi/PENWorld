# 01 進め方（人と AI の分担）

## 基本の型

| やること | なぜ |
|---|---|
| **1 つの PR = 1 つのテーマ**。マージは人がする | 何が入ったか人が分かる。戻すのも簡単 |
| **計画の紙（PLAN.md）を 1 枚持つ**。段階・見積もり・済み/のこり を毎回書きなおす | 会話が切れても、次の回がその紙だけで始められる |
| **ルールの紙（AGENTS.md / CLAUDE.md）に「ルール」と「どこに何があるか」**。機能を足したら 1 行足す | AI が毎回コードを読みなおさずにすむ（トークンの節約に一番効く） |
| **見本を 1 つ作る → 見てもらう → 広げる** | 地形は森 1 つ、キャラは 1 系統（犬）から。全部作ってから「ちがう」が一番高い |
| **「全部進めて」でも、まず計画だけ出す** | 合意してから作る。順番を入れかえやすい |
| 大きなファイルは **役割ごとに分ける**（7,000 行のクラス → 6 ファイル） | 1 回の作業で読む量が減る |
| 迷う選択は **選択肢を 2〜4 個にして聞く**（おすすめ付き） | 人は選ぶだけ。決まったことは紙に書く |

## PR の決まり（失敗から決めた）

- **出した PR にあとからコミットを足さない**。足す前にマージされて「入っていない」が 3 回起きた。追加は必ず新しい PR に。
- 前の PR がまだマージされていない時は、**前のブランチの上に重ねて**新しいブランチを作り、PR に「この PR だけで #○○ も入ります」と書く。
- 作業の最初に **「前の PR はマージされたか」を調べる**。マージ済みなら main から、まだならそのブランチから枝を切る。
- PR の本文：何をしたか / 絵（前後の比較）/ 確かめたこと / まだのこと。

## 報告の型

```
何を変えたか（PR のリンク）
何を確かめたか（ビルド・早送り・撮影）
確かめていないこと・気になる点（← 必ず書く）
次の候補（2〜3 個。順番を変えたければ言ってください）
```

- 受け取り方が 2 通りある頼み（例：「進化の変化がもっと欲しい」= 演出？ 姿の差？）は、**どちらと受け取ったか書いてから**進める。
- うまくいかなかった案も書く（「目を大きくしたら 2 つがくっついて見えたのでやめた」）。

## 人がやると良いこと（PULSAR でうまくいった頼み方）

- **見本は画面録画で渡す**。SNS のページは AI から読めないことが多い。動画はコマに切って見てもらえる（`tools/frames.sh`）。
- 「この感じが好き」に加えて、**どこが好きか一言**（「水の感じ」「絵の質感」）。違ったら「質感じゃない？」と言い直す。
- 大きさ・数の調整は **「もうちょい小さく」で十分**。AI は数字を 1 か所にまとめておけば 1 行で直せる。
- 寝る前・出かける前は「進めて」と一言。AI は候補を順に進めて、朝に報告と PR を残す。

## AI に守らせるルール（PULSAR の例）

- デザインはすべてオリジナル（実在のゲーム・キャラ・ロゴ・UI・効果音を再現しない）
- 公開リポジトリ：秘密・鍵・個人情報をコミットしない。外部通信を増やさない（CSP）
- セーブ・読みこんだデータは信用せず範囲を検査する。`innerHTML` に外部の文字を入れない
- 見た目の変更はスクリーンショット（PC とスマホの大きさ）で確認してから完了
- 作業の区切りごとに `npm run build`
- 重い効果は画質「低」で切れるように

## 1 日の流れ（例）

1. 人：見本 or 不満を 1 つ言う（「木がポリゴンっぽい」）
2. AI：原因を言葉にする → 直す → 撮って比べる → PR
3. 人：見て一言（「もうちょい小さく」）→ AI：新しい PR
4. 人：マージ。寝る前に「戦闘も進めて」→ AI：測る → 直す → PR を積む
