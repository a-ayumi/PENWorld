# 02 確かめ方（目で見る前に数で見る）

「テストではうまくいくのに、遊ぶとだめ」が何度も起きた。原因はたいてい **見ている物が違う** こと。

## 6 つの型

| 型 | 中身 | 見つかった例 |
|---|---|---|
| **早送り** | 描画を止めて `update(dt)` を数千回。2 時間ぶんが数分 | 戦争が 2 時間たっても決着しない |
| **数える** | 何回食べた・何分で勝った・止まったままの最長秒・はまった回数 | 食べ物は 40 個あるのに食べた回数が止まる → 届かない所に落ちていた |
| **行けるかの検査** | まんなかから塗りつぶし、**平らなのに行けない升目を 0 に** | 岩の壁のてっぺんが平らで行けない |
| **1 匹を追う** | 数秒ごとに 場所・状態・おなか・目標までの距離 を表にする | 「食べ物をめざす → 時間切れ → また同じ物」をくり返して倒れていた |
| **同じ絵を撮る** | 乱数を固定して同じ場面を作り、同じ角度で前後を撮る | 質感の前後比較 |
| **一覧を撮る** | 全キャラを 1 枚に並べる | 進化しても色と大きさしか変わっていない |

## 早送りの落とし穴（2026-11-17 に分かった）

- **1 歩を大きくすると、物理がうそをつく**。1 歩 0.5 秒の早送りで、木から落ちた食べ物がいつまでも跳ね続けて着地せず、
  「なかまが全員腹ぺこ」に見えた。ふつうの 1/30 秒では食べていた。
  → **おかしな結果が出たら、ふつうの歩幅でも測りなおす**。
  → ただし本物のバグでもあった（ゲームの「留守の間の早送り」も 0.5 秒だった）。**跳ねる・落ちる判定は 1 歩の大きさに比例させる**。
- 早送りで「数分で勝てた」のは条件をそろえたから。**新しいゲームのまま長く早送り**して、ふつうに遊んだ時の時間を測る。

## 調整の手順（例：戦争の速さ）

1. 新しいゲームを 120 分早送りし、10 分ごとに表を出す（なかま数・城の部屋・拠点の数・城の体力）
2. 決着しない → できごとのログを見る（部隊が出ている？ 取れている？）
3. 部隊が 10 秒でばらける → 1 匹を追う → 「おなかが少ないとすぐ帰る」と分かる
4. 直したら **同じスクリプトで** もう一度 120 分。数字が良くなったことを見る
5. 1 回の早送りは 1 回の結果。「ゲームごとに前後します」と書く

## 絵の確かめ方

- Playwright（ヘッドレス Chromium・SwiftShader）で撮る。ゲームに `window.__ゲーム名` の入口を作っておく。
- 撮る直前に JS を走らせる口（hook）を作る：カメラを置く・天気を固定・できごとを起こす。
- **撮った絵は必ず自分で見る**。数字だけで「直った」と言わない。
- PC（1280×800）とスマホ（390×844）の両方。

## 見本の動画をコマに切る

```bash
# 1 秒に 1 枚・幅 590
ffmpeg -i 見本.mp4 -vf "fps=1,scale=590:-1" f%02d.png
# 原寸で一部を切り抜き（幅:高さ:左:上）
ffmpeg -ss 2.5 -i 見本.mov -frames:v 1 -vf "crop=1180:670:0:822" crop.png
```

- SNS の画面録画は **画質の悪い版を渡されることがある**。ぼやけた絵で判断すると間違える（「平らな塗り」と思ったら、きれいな版では描きこみがあった）。
- 自分の絵も同じ引き・同じ角度で撮って **並べて** 比べる。

## スクリプトの置き場

- しらべ用のスクリプトは **リポジトリに入れて使い回す**（`tools/test/`）。その場かぎりで捨てない。
- 使い捨ての「1 匹を追う」などは作業用フォルダに。役に立ったら tools に昇格。
