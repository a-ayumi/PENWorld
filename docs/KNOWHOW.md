# ゲームづくりのノウハウ（ほかのプロジェクトでも使える形で）

PULSAR（Three.js + TypeScript の 3D 液晶ペット）を AI と作ってきて わかったことを、**このゲームに かぎらない形**で まとめる。
このリポジトリだけの細かい作り方は `docs/TECHNIQUES.md`、これからの計画は `docs/PLAN.md`。

---

## 1. 進め方（人と AI の分担）

| やること | なぜ |
|---|---|
| **1 つの PR = 1 つのテーマ**。マージは人がする | 何が入ったかを 人が はあくできる。もどすのも かんたん |
| **計画の紙（PLAN.md）を 1 枚もつ**。段階・見積もり・済み/のこり を 毎回 書きなおす | 会話が とぎれても、つぎの回が その紙だけで 始められる |
| **決まりの紙（CLAUDE.md）に「ルール」と「どこに何があるか」を書く**。機能を足したら 1 行足す | AI が 毎回 コードを読みなおさずに すむ（トークンの節約に いちばん効く） |
| **見本を 1 つ作る → 見てもらう → 広げる** | 全部作ってから「ちがう」と言われるのが いちばん高くつく。地形は森 1 つ、キャラは ねこ 1 系統から |
| **「全部進めて」と言われても、まず計画だけ出す**（段・中身・見積もり） | 合意してから作る。あとで順番を入れかえやすい |
| 大きなファイルは **役割ごとに分ける**（例：7,000 行のクラス → 6 ファイル） | 1 回の作業で読む量が へる |

### PR を重ねる時の落とし穴
- 前の PR が マージされる前に 次を作る時は、**前のブランチの上に重ねる**。その時は「A → B の順にマージ。B だけでも A ごと入る」と 必ず書く。
- **PR を出したあとに 同じブランチへ コミットを足す時**は、足したことを はっきり伝える。伝えないと、足す前の状態でマージされて「直ってない」となる（じっさいに 島を広げたコミットが入らず「狭い」と言われた）。
- 作業の最初に **「前の PR は マージされたか」を しらべる**。マージ済みなら main から、まだなら そのブランチから 枝を切る。

### 伝え方
- 報告は「何を変えたか → 何を確かめたか → **確かめていないこと**・気になる点 → つぎ」の順。
- 受け取り方に 2 通りある たのみ（例：「進化時の変化がもっと欲しい」= 演出？ 姿の差？）は、**どちらと受け取ったかを書いてから**進める。
- うまくいかなかった案も 書く（例：目を大きくしたら 2 つが くっついて見えたので やめた）。

## 2. 確かめ方（目で見る前に 数で見る）

**「早送りの しらべ」では うまくいくのに、あそぶと だめ**、が 何度も起きた。原因は 見ている物が ちがうこと。

| 型 | 中身 | 見つかった例 |
|---|---|---|
| **早送り** | 描画を止めて `update(0.1)` を数千回。15 分ぶんが 数十秒 | 生き物が 崖の前で 14 秒 止まる |
| **数える** | 「歩いた升目の割合」「止まったままの最長秒」「はまった回数」「たからばこが あいた数」 | 3 つのうち 1 つしか あかない → 坂の上に 段差が のこっていた |
| **行けるかの検査** | まんなかから 塗りつぶしで 行ける升目を数え、**平らなのに行けない升目を 0 にする** | 岩の壁のてっぺんが 平らで行けない |
| **1 匹を追う** | 1 秒ごとに 場所・状態・高さを 表にして出す | 坂の「わき」に それて 上がれない |
| **同じ絵を撮る** | 乱数を固定して 同じ村を作り、同じ角度で 前後を撮る | 色・木・道の 前後の見比べ |
| **一覧を撮る** | 全キャラを 1 枚に ならべる | 進化しても 色と大きさしか 変わっていない |

- しらべ用のスクリプトは **リポジトリに入れて 使い回す**（`tools/test/`）。その場かぎりで捨てない。
- デバッグ用の入口（`window.__pulsar` のような 1 つの物）を作っておくと、どのスクリプトからも 中身に さわれる。
- 「直した」と言う前に、**直す前に だめだった数が 直したあと 良くなったこと**を 同じスクリプトで見る。
- 撮っていない・あそんで確かめていない時は、そう書く。

## 3. 見た目を 見本に寄せる

1. **見本を 言葉に ばらす**。「この感じ」のままでは作れない。動画なら コマを切り出して：色（彩度・明暗の幅・影の色）/ 光（影の長さ・かたさ）/ 木や草の形 / 物の密度 / 建物の細かさ / 地形。
2. **効きめが大きく 手間が小さい順**に ならべる。たいてい：
   1. 仕上げ（ポストエフェクト）の色と光 … 1 か所で 全体が変わる
   2. いちばん数の多い物（木）の形
   3. 物と物を つなぐ物（道・階段・小物）
   4. 1 つ 1 つの細かさ（建物）
3. **雰囲気だけを目ざし、形は まねしない**（オリジナル）。

### 使えた技
- **色の落ち着かせ方**：彩度を下げる（0.7〜0.8）→ 緑だけ オリーブへ寄せる → 影は 紫でなく茶へ → 明暗の幅を しぼる（まっ白・まっ黒を作らない）。色の段数は ふやす。
- **仕上げで くすむぶん、元の色は 少し鮮やかめに**ぬる（葉を そのまま塗ると 灰色になった）。
- **輪郭は 黒にしない**。となりの色を暗くした色にすると やわらかい。
- **光は 4 段**（影も まっ黒にしない）、太陽は 高め（影が短い）。
- **ふさふさの木**：丸い多面体を 7〜9 個かさね、面ごとに「上を向いた面ほど明るい」色を ぬって 1 つの形に まとめる。
- **地面の材質を 面ごとに分ける**（草 / 岩 / 雪）。色を テクスチャに かけるだけだと、岩も 草の色に 引っぱられる。
- **村の かざりは セーブしない**。家と建物の場所から 毎回 同じ形に作る（種 = 場所）。道は 実際の道さがしの結果に 石を ならべると、歩く所と 道が そろう。

## 4. 地形と 歩き

- **元の大きさで形を決めて、倍率で広げる**（20 マスの島で形を作り `k = 広さ / 20` 倍）。広げても つりあいが くずれない。ただし **高さは 自動では広がらない**ので 別に上げる（広げたら 山が低く見えた）。
- **升目（0.5 マス）と A\***。まっすぐ行ける時は 道さがしを しない（重さの節約）。1 フレームの回数に 上限。
- **のぼりと おりを 分ける**：のぼれる段差は 小さく、とびおりは 大きく。「段差で 身動きが取れない」が ほぼ消える。
- **はまり対策は 3 だん**：行けない向きは 横へ すべらせる → まわりの どこにも行けなければ 出す → 崖に ぶつかったら **いまの場所から** 道を さがしなおす（道から それた時に 効く）。道が無い目的地は すぐ あきらめる。
- **「通れないせいで 行けない 平らな所」を作らない**。飾りの山や崖の斜面は 行けなくてよい。
  - 坂は **崖が立ちあがる前に のぼりきる**（最後に 1 段のこりやすい）。
  - 坂は **幅いっぱい 同じ高さ**（わきが低いと、それた子が 上がれない）。
  - 壁のてっぺんは **とがらせる**（平らだと 行けない平地になる）。
- **足もとの高さは「まわりで いちばん高い所」**。まんなか 1 点だと 坂に めりこんで見える。
- **木の当たり判定は 見た目より小さく**、道をたどる時は よける幅を せまく。木を すきまなく ならべると 壁になる。
- 家や置き物は **急な坂を えらばない**。まんなかに 平らな広場を のこす。

## 5. キャラクター（コードで描く ドット絵）

- **流れ**：小さな座標（34×32）に 丸・四角・多角形で描く → 2 倍で焼く → 自動の陰影 → 色つきの輪郭。
- **全キャラに 一度に効くのは 仕上げだけ**。効きめは ひかえめ：
  - 陰影は「ふちからの距離」で ふくらみを作り、**影は寒色・光は暖色へ 色相をずらす**。
  - 輪郭は 光の側を うすく、影の側を こく。
- **はっきり良くするには、系統ごとに 専用の描き方を書く**（共通の「丸 + 部品」を やめる）。効いた点：
  - 頭を大きめに、**両目が顔の中に入る ななめ向き**（横顔に 点の目は 弱い）
  - 口もと・はな・ほおの毛・耳の内がわ の色
  - しっぽは 曲線に そって丸を ならべる（しなる）
  - 足に ふとももと 足先
  - 体は 共通、**頭だけ 入れかえる**（ねこの体 + いぬの頭）
- **進化の差は「色と大きさ」だけでは 伝わらない**。4 だんかいで 形そのものを変える：
  1. 赤ちゃん = 顔だけの ちいさな つぶ（体なし）
  2. 成長期 = ちいさな子ども（頭が大きく 足が短い）
  3. 成熟期 = 足の長い 大きな けもの + その子の特徴
  4. 完成期 = かざりと武装で べつものの姿
  - 体つきは 1 つの数（0〜1）から決める（足の長さ・頭の割合・きばの長さ）。かざりは データの指定で足す。
  - **箱庭での大きさも 段階で 大きく変える**（0.72 → 2.3）。
- 既存の仕組み（表情・もよう・色ちがい）は、描き方を入れかえても動くように **同じ形の値を返す**。

## 6. 作りの決まり（ほかでも そのまま使える）

- **セーブする物 / しない物を 分ける**。見た目だけの物は 状態から 作りなおす。セーブを ふやしたら 保存と読み込みの 両方を直す。
- **読みこんだ物は 信用しない**（種族の名前・数の範囲を しらべる）。
- **データの表にする**：種族・建物・置き物・目標・実績。足す時は 表に 1 行。
- **重い効果は 必ず 切りかえられるように**（画質 高 / 低）。
- **数の定数は 名前をつけて 1 か所に**（のぼれる段差・島の広さ・大きさの倍率）。調整が 1 行ですむ。
- ゆれ・フラッシュは「うごきを へらす」設定の係数を かける。
- 外への通信を ふやさない。ひみつを コミットしない。

## 7. 失敗と 学び（早見）

| 起きたこと | 学び |
|---|---|
| 島を広げたのに「狭い」と言われた | PR に あとから足したコミットは マージに入っていないかも。まず しらべる |
| しらべでは 宝箱が あくのに、あそぶと あかない | 確率まかせにせず、**人が さわれる入口**（タップで あけに行く）を作る |
| 段差で 動けなくなる | のぼり / おりを分ける + はまったら出す |
| 岩が 緑に見える | 色を テクスチャに かけている。材質を分ける |
| 目を大きくしたら 悪くなった | 一覧で 前後を見比べてから 入れる。だめなら 入れない |
| 進化が 色ちがいに見える | 形・大きさ・かざりを 段階で変える |
| ビルドが CI だけ落ちる | 手元も CI と同じ入れ方（`npm ci`）で そろえる |
| 外のページ（SNS）が 読めない | 画面の動画や スクショを もらう。コマを切り出して見る |

## 8. 新しいプロジェクトで 最初にやること

1. `CLAUDE.md`：コマンド・ファイルの地図・ルール（オリジナル・セキュリティ・確認のしかた）
2. `docs/PLAN.md`：方針・段階の表・作業の手順メモ
3. デバッグの入口（`window.__名前`）と、早送りできる `update(dt)`
4. `tools/test/`：早送り・同じ絵を撮る・一覧を撮る の 3 本
5. 見た目は 仕上げ（色と光）から。見本を 1 つ作って 見てもらう
6. 1 PR 1 テーマ。報告に「確かめていないこと」を書く
